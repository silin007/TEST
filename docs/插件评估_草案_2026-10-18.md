## 1. Windows Mouse Passthrough —— 实测可用，建议采纳

来源：<https://github.com/hubacekjakub/Godot-WinMousePassthrough>
协议 **MIT**，纯 C++ GDExtension，无需 .NET，仓库声明 Godot 4.3+。

### 1.1 它解决的正是架构里被标为「不能承诺」的问题

架构 §4.3 表：

> 整窗穿透 | `Window.mouse_passthrough` 文档描述涉及同一应用底层窗口，**不能据此承诺跨应用穿透**。

插件 README 对同一问题的说明：

> `Window.mouse_passthrough`（布尔标志）通过 `WM_NCHITTEST`/`HTTRANSPARENT` 实现，按 MSDN 仅转发**同线程**窗口的命中测试，不能可靠地把点击传给其它应用程序。

插件的直接对 HWND 设置 `WS_EX_LAYERED | WS_EX_TRANSPARENT`（两者必须同时设置，仅 `WS_EX_TRANSPARENT` 无效）。这与本轮 P0-006 探针实测到的 `WINDOW_HANDLE` 原生句柄可用是同一条技术路径。

### 1.2 4.7.2 兼容性实测（关键）

插件预编译 DLL 是针对 **godot-cpp 4.6-stable** 构建的，而本项目是 4.7.2，ABI 兼容性不能靠猜。实测结果：

```
=== GDExtension 加载实测（Godot 4.7.2-stable (official)）===
Engine.has_singleton("MousePassthrough") = true
singleton = <MousePassthrough#9193914600>
window_id = 0
调用 set_passthrough(id, true) ...  → 成功
调用 set_passthrough(id, false) ... → 成功
```

headless 与真实窗口（D3D12）**两种模式均通过**。

**一个必须注意的坑（实测踩到）**：首次放置后直接运行，探测结果为 `false`；必须先执行一次 `--import` 让引擎扫描到 `.gdextension` 文件后才加载成功。导出构建时不存在此问题（导出会打包 `.gdextension`），但**编辑器内首次引入必须重新导入**。

**另一个集成成本**：本项目开启全静态类型检查（`enable_all_warnings`），GDScript 无法静态推导 GDExtension singleton 的方法：

```
Parse Error: The method "set_passthrough()" is not present on the inferred type "Object"
```

必须用 `Object.call("set_passthrough", id, true)` 动态调用并包一层封装。

### 1.3 风险（作者自述，须登记）

> Also, it's fragile: **the engine can update the window style and clear the flags**.

即引擎自身更新窗口样式时可能清除扩展设置的标志，需要在模式切换后重新应用。此外：

- 第三方二进制 DLL 入库（MIT 允许，但需保留 LICENSE、并在导出模板中包含 DLL）
- 跨应用穿透的**实际效果仍须人工验证**（让宠物窗口压住记事本/浏览器后点击），自动化无法替代，这正是 WIN-02 的取证要求

### 1.4 建议落点

挂在 `WindowController`（不是 `Main.gd`，本项目无此文件），作为 `set_mouse_mode_internal()` 的 Windows 通道：

- 有 `MousePassthrough` singleton → 用它设系统级穿透
- 无 singleton（Linux/macOS 或加载失败）→ 回退现有 `Window.mouse_passthrough`，并在诊断中标注为「仅同应用」

## 2. Maaack's Game Template —— 不采纳

来源：<https://github.com/Maaack/Godot-Game-Template>，协议 **MIT**（Copyright Marek Belski），v1.7.0，声明 Godot 4.4+。

### 2.1 事实更正：它的存档不是 JSON

你的描述是「借用其已经写好的 JSON 配置文件读写逻辑」。实测源码 `base/nodes/state/global_state.gd`：

```gdscript
const SAVE_STATE_PATH = "user://global_state.tres"
static func save() -> void:
    if current is GlobalStateData:
        ResourceSaver.save(current, SAVE_STATE_PATH)
static func _load_current_state() -> void:
    if FileAccess.file_exists(SAVE_STATE_PATH):
        current = ResourceLoader.load(SAVE_STATE_PATH)
```

它用的是 **Godot Resource（`.tres`）**，不是 JSON。

### 2.2 更关键：它没有任何事务安全，会回退刚修好的 P0-001

`ResourceSaver.save()` **直接覆盖目标文件**：无临时文件、无备份、无写入前校验、无失败回滚、无隔离区、无 schema 版本校验（`current_version` 只作记录，不作校验）。

对照本项目刚修复的 P0-001（未知版本存档被自动覆盖）——采用该模板会**直接回退这个修复**，且无法满足架构 §7 与 SAVE-01～08 要求的「tmp → 复核 → 备份 → 提交 → 提交后复核 → 清理」事务协议。

### 2.3 与本项目架构冲突

模板核心依赖多个 **Autoload 全局单例**（`AppConfig`、`SceneLoader`、`GlobalState`、`AppSettings`）。而本项目架构明确：**AppController 为唯一装配根节点，无 Autoload 全局事件总线**。引入即与装配结构冲突。

### 2.4 场景管理器不适用

你设想用它处理「完全体窗口 ↔ 悬浮球」切换。但 MOTE 的模式切换是**同一窗口的属性切换**（尺寸/位置/穿透/焦点），不涉及场景加载。用 `SceneLoader` 反而引入加载屏、线程加载、场景生命周期等无关复杂度。

### 2.5 附带成本

该模板面向 game jam，含主菜单、暂停菜单、credits、开场动画、关卡加载、手柄输入、itch.io 发布脚本等大量与桌宠无关的资产。

## 3. Godot State Charts —— P0 不采纳

来源：<https://github.com/derkork/godot-statecharts>，协议 **MIT**，v0.22.5，声明 Godot 4.0.4+。

### 3.1 与架构 §5.2 的效用 AI 直接冲突

架构 §5.2 明确规定的是**效用评分**而非状态机：

> 其余候选评分：idle=`0.25`；walk=`0.15+0.60*activity`；look_around=`0.15+0.60*curiosity`。
> idle/walk/look_around 最短持续分别为 5/6/4 秒；walk 与 look_around 各有 10 秒冷却。

验收用例 SIM-01～04、PET-03①②③ 全部围绕这套评分与冷却设计。改用 State Chart 会推翻 §5.2 的全部数值设计与对应验收用例，属**架构级变更**，不是替换一个内部实现。

### 3.2 与「纯逻辑、不依赖场景树」的现有基础冲突

State Chart 是**节点化**方案，状态和转移都是节点，必须进场景树。而本项目 `PetSimulation` / `UtilityAI` / `ActionExecutor` 是**纯逻辑模块，不依赖场景树**——这是 P0 测试能在 headless 下全量运行、并被架构认可的基础。改为节点化会损害这一特性。

### 3.3 若确有需要

State Chart 本身质量不错（MIT、有编辑器内调试视图、支持延迟转移与表达式守卫）。可作为 **P1 的动画层状态管理**候选（动画状态确实是离散的），与 UtilityAI 决策层分工。但需先修订架构明确分层，本草案不实施。
