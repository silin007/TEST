# MOTE 插件复评与设计调整建议

日期：2026-10-18。对象：`插件评估_草案_2026-10-18.md` 中的三个插件。

**结论：MousePassthrough 优先采用，但须补可靠性；Maaack 可选择性复用设置界面；State Charts 可与 UtilityAI 共存，适合后续复杂执行流程。原草案对后两者的否定过于绝对。** 应依据实际节省的开发、排错和维护工作决定采用范围，而不是因为初始架构写过另一种实现就排除插件。

本次完成本地代码审阅、上游源码和官方资料核查，未安装新插件、未修改产品逻辑或架构验收基线，未重新执行兼容性或跨应用穿透实测。附件中的待确认事项作为评估输入，不视为用户要求立即安装或改写实现。

## 1. 决策总表

| 插件 | 本项目的实际收益 | 接入与维护成本 | 建议决定 | 是否值得改设计 |
|---|---|---|---|---|
| Windows Mouse Passthrough | 补原生跨应用穿透通道，避免自行从零开发 Windows 扩展 | 小范围接入；需 DLL 打包、错误回读、样式变化后恢复和实机回归 | **优先采用，完成可靠性后作为 Windows 穿透后端** | **值得**：允许必要的 C++ GDExtension；保留 GDScript 业务层 |
| Maaack's Game Template | 成批生成设置行、音频选项、输入映射等界面与连接逻辑 | 整包迁入高；抽取组件中等；现有简单面板收益有限 | **可用，按组件引入；当前不迁移整个应用** | **局部值得**：设置 UI 与持久化适配可调整，核心存档无需迁移 |
| Godot State Charts | 层级/并行状态、事件转移及编辑器调试，减少复杂执行流程的手写分支 | 简单流程接入反而更重；复杂流程逐步受益 | **可用，先作为 P1 执行流程候选；P0 保留现有实现** | **值得保留调整空间**：执行器可以节点化，决策核心不必改 |

以上是工程判断，不是已经测出的开发耗时。未用“插件功能更多”替代收益评估，也不把既有代码投入本身作为拒绝理由：关键是未来剩余工作能否少于迁移和长期适配工作。

## 2. 哪些原设计可以改

| 设计项 | 判断 | 本次建议 |
|---|---|---|
| 完全只用 GDScript / 不用原生扩展 | 实现选择，可改 | Windows 能力需要时允许小型 GDExtension，业务规则仍在 GDScript |
| 所有控制器都必须纯逻辑 | 原架构并未这样要求 | PetSimulation、UtilityAI 保持独立；执行与表现层可用 Node |
| 不使用任何 Autoload | 原文是“不将所有模块都做成 Autoload、不使用全局事件总线” | 可允许少量职责单一的服务；不为了模板同时引入第二套状态所有权 |
| 单一主窗口 / 不用 SceneLoader | 可改，但当前没有改动收益 | 设置页可切换子场景；无需销毁应用根、模拟器或主窗来切换模式 |
| 全部设置必须放一个 JSON | 可以拆，但需明确恢复规则 | 核心生命状态继续可靠存档；未来语言/音量等可独立配置，窗口恢复设置继续走明确安全规则 |
| UtilityAI 的评分参数、动作时长、冷却 | 可调整的玩法基线 | 只有新行为设计带来收益才调整，并同步预期；不为状态图库而删除评分 |
| Skeleton2D 表现 | 当前项目的明确 P0 目标 | 三个插件都不要求替换，没必要改 |
| 离线基础生命、唯一核心状态写入方、存档不静默覆盖、隐藏/穿透后可恢复 | 产品可靠性要求 | 保留结果要求；具体技术实现可以更换 |

JSON 本身不是可靠性的来源；Resource 或 ConfigFile 也可设计成可靠存储。当前不替换 SaveService 的理由，是这些插件没有现成覆盖本项目已经要求的恢复协议，换格式后仍需补相同工作。

## 3. MousePassthrough：采用方向正确，原草案高估了当前证明程度

### 3.1 能节省什么

插件提供直接设置 Windows 窗口扩展样式的通道；Microsoft 文档确认 layered window 结合 WS_EX_TRANSPARENT 会把鼠标事件传至下面窗口。这是与当前需求匹配的方案，值得采用，并不要求改变生命模拟或角色表现。[Microsoft：Layered Windows](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features#layered-windows)

上游说明采用 C++ GDExtension，预编译包使用 godot-cpp 4.6-stable。它只处理鼠标穿透，不负责托盘、窗口隐藏或 DPI。当前本地描述文件仅列 Windows x86_64 debug/release 两个库；不能由此声明 ARM64 或其他平台受支持。[上游项目说明](https://github.com/hubacekjakub/Godot-WinMousePassthrough)

### 3.2 已发现的集成缺口

本地现状已不同于草案“未修改产品代码”的末尾说明：WindowController 和 AppController 工作区已经有 singleton 调用及诊断改动，本次保留这些未提交改动。

- **成功判定不足。** 上游 set_passthrough 返回 void，HWND 为空时直接返回，Windows API 结果未检查。本地 `_set_system_passthrough()` 在调用后无条件返回 true，继而显示 system。这个值最多证明“调用已发出”，不能证明样式或跨应用点击生效。[上游实现](https://github.com/hubacekjakub/Godot-WinMousePassthrough/blob/cb450b9d9618559b36aeedd4699dfbc5066bcbb1/gdextension/src/mouse_passthrough.cpp)
- **恢复也应验证。** 关闭穿透同样没有成功回读；否则 UI 可能显示可交互，原生窗口仍穿透。应将开启和关闭都纳入模式事务，失败返回明确错误并走恢复路径。
- **属性顺序需要整理。** 当前 apply_mode 在设置穿透之后仍更新焦点策略。若窗口属性变化清除扩展样式，先设穿透就可能失效。应完成尺寸、置顶、焦点等属性后再应用最终穿透；窗口重建、还原和唤醒后重新核查，不逐帧盲目设置。
- **回退不能冒充达标。** 扩展缺失时保留内建方案可帮助开发和排错，但不能宣称 P0 的跨应用穿透仍完整。目标 Windows 构建若无法提供承诺能力，应拒绝相应模式或明确显示能力不可用，并保留恢复入口。
- **探针存在假通过可能。** 现有 `probe_mousepassthrough.gd` 在 singleton 不存在时仍 quit(0)，且调用后只打印成功。它不是能判定功能通过的验收测试；headless 也不能证明桌面命中。

推荐对这个小型扩展做最小维护分支：返回错误/结果，提供样式回读，区分 requested、native_flags_verified、external_click_tested。flags 回读仍不等于底层应用实际收到点击。关闭时上游只移除 TRANSPARENT、保留 LAYERED；应与 Godot 的透明样式所有权协调，不能简单清除全部样式位。

### 3.3 最小采用范围与完成条件

只在 WindowController 后增加 Windows 适配器，不让平台调用进入模拟。保留 MIT LICENSE，固定上游提交和 DLL 哈希，记录构建方法；最终构建验证 DLL 随包可加载。DLL 由导出包分发，不要求修改官方导出模板。当前 `.gitignore` 整体忽略 addons 不适合作为长期依赖策略，应改为精确规则或固定版本的可复现获取流程。

完成条件是：独立导出程序中，覆盖宠物不透明区域的点击/滚轮能到达外部应用；托盘能恢复交互；反复切换 FULL/FOCUS/HIDDEN、最小化恢复和睡眠后仍一致；DLL 缺失、原生失败和关闭失败能被识别。通过这些检查后，可关闭相应能力缺口。本轮没有执行这些操作，不能宣布 WIN-02 已通过。

## 4. Maaack：从“整包不合适”改为“组件可以有价值”

### 4.1 原草案需要更正的判断

GlobalState 的实现确实保存 `global_state.tres`，所查包装代码没有本项目的备份、隔离及 schema 拒绝流程。**完整替换核心保存流程会丢失现有保证；仅复用界面不会自动回退 P0-001。** 不能由一个不适用的模块推导整个模板不可用。[GlobalState 源码](https://github.com/Maaack/Godot-Game-Template/blob/6849d6c352dafe8ed54b5fa4f4b9774adfca31c8/addons/maaacks_game_template/base/nodes/state/global_state.gd)

设置系统与 GlobalState 不是同一个入口：官方设置文档提供可组合的滑条、开关等选项控件，并接到 PlayerConfig。只需要设置面板时，可复用控件模式，或者替换其读写适配。[Options Menu Setup](https://github.com/Maaack/Godot-Game-Template/blob/6849d6c352dafe8ed54b5fa4f4b9774adfca31c8/addons/maaacks_game_template/docs/OptionsMenuSetup.md)

### 4.2 是否值得为它改设计

**值得考虑的改动：** 将 FULL 从诊断页发展为分栏设置页，采用统一的选项行；通过设置适配层读写 MOTE 设置。如果未来已有语言、音量、显示、输入等多组重复选项，复用收益会更明显。

**当前不建议的改动：** 把整个项目搬入模板，或者为了模板改成通过 SceneLoader 重建应用。MOTE 当前主要是同一原生窗口的模式切换，模板不能替代这部分 Windows 工作。

音量等低风险偏好将来可以使用独立配置文件并允许损坏后回到默认；宠物状态仍由 SaveService 负责。若某个设置同时出现在两个文件，必须指定唯一写入方和优先级。模板 AppSettings 含直接修改全屏和分辨率的代码，这些行为应经 WindowController 执行，避免绕过 MOTE 模式事务。[AppSettings 源码](https://github.com/Maaack/Godot-Game-Template/blob/6849d6c352dafe8ed54b5fa4f4b9774adfca31c8/addons/maaacks_game_template/base/nodes/config/app_settings.gd)

建议在正式设置需求明确时，用真实的“音量、语言、穿透偏好”三项做隔离小样；比较抽取依赖、主题适配和保存接线的工作量。若仅几项开关，原生 Control 直接写通常更轻。该判断是成本预期，尚无本项目小样计时证据。授权方面除代码协议外，抽取字体、音效等资产还应逐项查看归属，不能把整包资产一概当作同一许可。

## 5. State Charts：可以共存，是否现在迁移取决于复杂度

### 5.1 它不是 UtilityAI 的替代关系

UtilityAI 回答“现在选择什么”；State Charts 可以回答“选中后经过哪些步骤、如何中断、什么时候结束”。例如评分选择 rest，状态图执行“坐下 → 睡眠 → 被唤醒 → 起身”。评分、性格、需求和动作结果仍可以沿用，不必重写全部玩法数值。

上游 StateChart 是 Node，支持事件和表达式属性，提供编辑器跟踪和显式 step；节点化不等于不能 headless 测试。代价是相关测试需要场景树生命周期，不再是纯对象测试。send_event 也不保证返回时所有处理已经完成，不能当成同步平台操作的成功结果。[StateChart 源码](https://github.com/derkork/godot-statecharts/blob/76d226a3efac66a72aea825382b320c94808f409/addons/godot_state_charts/state_chart.gd)

### 5.2 可以怎样调整

保留 PetSimulation/UtilityAI 的纯逻辑和 PetState 唯一写入；允许 ActionExecutor 内部改成节点化状态图，以接口适配保持 execute/cancel/tick 和实例结果事件。动画层继续使用 AnimationPlayer，不需要更换骨骼。

必须保留 action_instance_id、迟到结果拒绝、奖励只发一次、取消/超时回退。不要把休息锁定和需求计算复制到状态图，形成第二套决策规则。对动画表现的状态可以逐帧更新；决定奖励和行为时长的计时仍应由模拟 tick 驱动。存在 step 接口不代表所有延迟转移自动遵循模拟时间；接入时要核实具体计时链路，不能接入后默默使用另一只时钟。[延迟转移源码](https://github.com/derkork/godot-statecharts/blob/76d226a3efac66a72aea825382b320c94808f409/addons/godot_state_charts/transition.gd)

### 5.3 为什么当前保留现状

现在执行器只是短小的动作生命周期，迁移仍要处理同样的计时、取消和结果校验，节省有限。等出现多阶段动作、多个可并行表现层、频繁中断、或非程序成员需要维护流程时，状态图与调试视图才更可能省时间。

若确实把产品改为少量预设反应、取消性格评分与自主选择，才值得讨论用状态图替代 UtilityAI；这会改变数字生命的行为表达，不能仅为方便使用插件而默认采用。当前推荐的是“评分决策＋状态图执行”的可选扩展路线。

## 6. 现在如何推进

1. **P0 先完成 MousePassthrough 后端可靠性及跨应用/恢复实测。** 这是当前直接补能力缺口的投入；同步架构中的平台路径和验收证据，不降低结果要求。
2. **P0 验收期间暂不迁移设置系统与行为执行器。** 不是兼容性禁止，而是这两项暂时不能帮助关闭当前窗口、平台和稳定性缺口。
3. **P1 设置页出现成组重复选项时，试 Maaack 的最小组件。** 采用成功后修订设置存储边界与装配方式，仍由窗口控制器统一处理桌面模式。
4. **P1 动作流程出现明显层级与中断复杂度时，试 State Charts。** 先迁移一个真实多阶段动作，并验证旧事件、取消、模拟时间和 headless 测试；保留纯逻辑决策。

设计变动应以“同一需求更少代码、更好排错、更低维护成本”为标准；插件不要求把可靠存档、后台可恢复或离线生命这些结果要求改弱。
